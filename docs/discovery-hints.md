# 关键词 / 负向名单词表（v1）

**关键词不参与准入。** 结构指纹才是准入依据（GLOSSARY「结构指纹」，PRD §4.3、
spec #7 §发现管线）。这份词表只做两件事：

| 段 | 作用 | 能不能改变「是否进候选」 |
|---|---|---|
| `nameKeywords` | 给**已经进列**的候选排序 | **不能** |
| `negativeNamePatterns` | 把已进列的候选降权到「低」并标为「疑似」 | **不能**（只降权，不取消入列） |

安装佐证**不看这份词表**（issue #19）：它来自规则文件声明的安装路径，与用户词表配得全不全无关。

一个名字里含 `claude` 却没有任何结构特征的目录，**根本不会出现在候选列表里**
（User Story 8、9，PRD A1）。词表因此永远拿不到「让噪声目录进候选」的能力。

## 格式

JSON。放在应用支持目录下，随版本一起更新；路径由调用方给出（`DiscoveryHints.load(from:)`），
本层不猜路径、不读 `NSHomeDirectory()`。

```jsonc
{
  "schemaVersion": 1,                       // 必填，必须等于当前支持版本
  "nameKeywords": {                         // 可选：工具标识 → 关键词
    "claude-code": ["claude", "anthropic"],
    "codex-cli": ["codex", "openai"],
    "cursor": ["cursor"]
  },
  "negativeNamePatterns": [                 // 可选：已知易误判的名字
    "*bak*",
    "*backup*",
    ".claude-*",
    ".codexbar",
    ".codexhost",
    ".antigravity_cockpit"
  ]
}
```

- 两个段都可以省略；省略后分别表示「不参与排序」与「没有负向名单」。
- 未知字段一律忽略，词表可以向前兼容。
- **词表错了要报错，不静默降级成空词表**：空词表不会让功能出错，只会让负向名单
  悄悄失效、旧快照悄悄变成高置信度候选——那正是本票要防的失败模式。

## 模式写法

单段内的通配符，`*` 匹配任意字符，**忽略大小写**；没有 `?`、没有字符类、不跨 `/`。
逐段比对路径的每一段，因此 `.claude-tap` 这类**带前导点**的名字要连点一起写。

**比对范围到主目录为止**：判定的是**主目录之下、直到工具根**的那几段，工具根自身的名字
一定在内。主目录**本身及以上**的段（`Users`、用户名、以及主目录目录名）都不参与比对——
否则一个叫 `…-backup/Users/x` 的主目录会把该目录下每一个候选都降权成疑似，界面还会写
「命中负向名单 `*backup*`」，而那条路径本身没有任何问题。规则声明的路径若不在主目录之下，
则只比对它的最后一段：宁可漏判降权，也不误判——降权会挡住用户看见真正的高置信度候选。

写负向名单时**按实测名字写**，不要照抄记忆里的形态。实测里最容易踩的一条：

| 写法 | 能匹配 `~/.claudebak` 吗 |
|---|---|
| `*-bak` | ❌（它结尾是 `bak`，中间没有短横线） |
| `*.bak*` | ❌（它里面没有 `.bak`） |
| `*bak*` | ✅ |

PRD §4.3 列的是 `*-bak`、`*.bak*`、`*-backup*` 这一族形状，而实测存在的旧快照目录
是 `~/.claudebak`（798M）。因此默认词表里额外写了 `*bak*`；同理伴生小工具
（`~/.claude-tap`、`~/.codexbar`、`~/.codexhost`、`~/.antigravity_cockpit`）
应该逐个写全名，而不是靠 `claude*` 之类的粗放模式。

## 扫描范围：由规则决定，不枚举通用位置（issue #18）

浅扫**不再枚举任何通用位置**（PRD §4.2）。它只对规则文件声明的工具根做存在性判断与结构指纹比对。
「`~` 下只看隐藏目录」那道筛选口径随之一起下线——它当初存在是因为要把 `~` 列一遍才需要划范围；
不再列举 `~` 之后，范围完全由规则说了算。

换掉的理由是量化的：按旧清单列举，本机合计约 1,400 个一级目录（`~/Library/Containers` 一处
就 728 个），而这层枚举**几乎不产生任何候选**——准入要求命中规则声明的工具根，而那些目录
本来就没有规则声明它们。为了找 5 个已知工具扫了 1,400 个无关目录，观感上还让产品退化成一个
通用硬盘清理器。

**这条与词表无关**：词表从来不是准入依据，现在也不是扫描范围的依据。规则文件才是。

spec #7 / US2 写的「浅扫只遍历一级子目录」在这个口径下不再是偏差描述——DeepSeek Harness 的
真实工具根 `~/Library/Application Support/deepseek-harness-desktop/harness-home` 是那一层目录的
**孙子**（PRD §14.5），OpenCode 的数据根在 `~/.local/share/opencode`，它们能被找到是因为
**规则直接声明了那个路径**，不是多下潜了几层。代价边界有断言钉住：声明路径缺失时，
浅扫一次目录都不会列举，包括缺失声明路径的父目录。

## 关键词之外还有一类证据：安装检测

安装佐证来自**规则文件声明的安装路径**（`ToolRule.installations`，issue #19；PRD §4.3「关联检测」）：
发现器对每条声明逐条 `stat`，命中即产生佐证。它**先于打分执行**，是发现的**入口**与排序依据，
也是「高」置信度的佐证来源（User Story 10）。

**不得列举通用位置，包括 `/Applications` 与 PATH**（`~/Applications` 同理），也不得列举主目录。
一次发现对磁盘的访问只允许落在「规则声明的工具根内部」与「规则声明的安装路径本身」上
（验收 1）。安装佐证因此**不看这份词表**：声明属于哪条规则，就是哪条规则的证据——
早先「先按目录名筛关键词、再拿关键词去找同名 App / PATH 命令」的做法连同通用位置的列举
一起下线了。词表仍然管候选的同档排序，本阶段也**不发起任何网络请求**（User Story 45）。

**安装检测不是过滤器**：声明的安装路径都不存在时，不得跳过该工具的工具根检查。
卸载了工具、磁盘上会话还在，正是这个产品最该帮用户发现的场景——这种候选仍然出现，
只是拿不到安装佐证、停在「中」。
